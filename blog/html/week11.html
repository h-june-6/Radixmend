[RadixMend 11주차·선행] 안 쓰는 상위 비트에 ECC 넣기

모듈 B는 원래 11~12주차 일정이다. 그런데 인코딩 자체는 순수 계산이라 GPU 없이 먼저 만들고 검증했다. 인덱스를 쓰고 읽는 곳 목록도 1주차 코드 분석 때 대부분 정리해 뒀다.

이번 주에 하기로 한 것 (WBS)과 진행 상황

항목 상태
인덱스 텐서를 쓰는 곳 전수 목록화 코드 분석으로 초안 완료
디코드할 choke point 설계 후보 확정
안 쓰는 상위 비트에 SECDED 인코딩 구현 구현, 전수 검증 완료

왜 인덱스까지 지키나

KV 슬롯 번호가 깨지면 KV 값 하나가 깨지는 것보다 훨씬 위험하다. 상위 비트가 뒤집히면 KV 풀 밖을 읽어서 엔진이 죽는다. 하위 비트가 뒤집히면 다른 요청의 멀쩡한 슬롯을 읽어서, 요청끼리 데이터가 섞인다.

다행히 슬롯 번호는 비트를 다 안 쓴다. A6000에 8B 모델을 올리면 KV 풀이 대략 20만 슬롯이라 18비트면 된다. int32면 13비트가 남는다.

비트 배치

bit:  31   30..29   28   27 ........ 23   22 .................... 0
      부호  (안 씀)  전체   해밍 체크 5비트    슬롯 번호 23비트 (그대로)
      =0            패리티
  • 슬롯 번호를 아래쪽 비트에 그대로 둔다. v & data_mask가 곧 슬롯 번호다.
  • 그 위에 해밍 체크비트 5개와 전체 패리티 1비트를 붙여서 확장 해밍(SECDED)을 만든다.
  • int32에는 슬롯 번호를 최대 25비트(2^25 슬롯)까지 넣을 수 있다. int64는 56비트까지 된다.

데이터를 제자리에 두면 좋은 점이 두 가지다. choke point에서 디코드하는 게 마스크 한 번과 XOR 몇 번으로 끝난다. 그리고 어딘가에서 디코드를 빠뜨리면 상위 비트 때문에 값이 범위 밖으로 튀어서, SGLang 저장 커널의 device assert에 걸려 바로 멈춘다. 몰래 다른 슬롯을 읽는 일은 없다.

트러블슈팅

1. 해밍 코드를 교과서대로 넣으면 슬롯 번호가 흩어진다

문제. 교과서식 해밍 코드는 체크비트를 1, 2, 4, 8번째처럼 2의 거듭제곱 자리에 끼워 넣는다. 그렇게 하면 데이터 비트가 사이사이로 흩어져서, 슬롯 번호를 쓰려면 매번 비트를 다시 모아야 한다. 디코드를 빠뜨린 경로가 있으면 완전히 엉뚱한 슬롯을 읽게 된다.

해결. 같은 해밍 코드를 systematic 형태로 바꿨다. 데이터 비트 i에 "2의 거듭제곱이 아닌 i번째 값"을 열로 배정하고, 체크비트는 데이터 위쪽에 따로 모았다. 교정·탐지 능력은 똑같고, 슬롯 번호는 아래쪽에 그대로 남는다.

cols = [v for v in range(1, 1 << r) if v & (v - 1)]   # 2의 거듭제곱 제외
data_cols = cols[:data_bits]

2. SGLang이 쓰는 -1과 0

문제. SGLang은 "값 없음"을 나타낼 때 -1을 쓰는 곳이 있고, padding 슬롯으로 0을 쓴다. 인코딩된 값이 이 특수값과 겹치면 안 된다.

해결. 두 가지 다 자연스럽게 풀렸다. -1은 모든 비트가 1이라 부호 비트가 켜져 있는데, 인코딩된 값은 부호 비트를 항상 0으로 두니까 겹칠 일이 없다. 디코드 함수는 음수를 그대로 통과시키면 된다. 0은 선형 코드라서 0의 코드워드가 그대로 0이다. 그래서 SGLang이 torch.zeros로 만든 버퍼, padding 슬롯 0, req_to_token의 빈칸이 모두 따로 초기화하지 않아도 유효한 코드워드다.

3. int32에 얼마나 넣을 수 있나

문제. req_to_token은 int32인데, 부호 비트까지 건드리면 위의 -1 구분이 깨진다. 그러면 슬롯 번호는 몇 비트까지 넣을 수 있을까?

해결. 해밍 체크비트 r개로 감당할 수 있는 데이터 비트는 2^r − 1 − r개다. r=5면 26비트인데, 전체 패리티 1비트와 부호 비트를 빼야 하니 25 + 5 + 1 = 31비트가 int32에서 쓸 수 있는 최대다. 그래서 KV 풀 상한은 2^25(약 3,355만) 슬롯이 된다. 26비트를 넣으려고 하면 에러가 나도록 했고, 테스트로도 확인했다.

4. FlashAttention 3에서는 상위 비트가 커널까지 그대로 간다

문제. 코드를 보니 FlashAttention 3 백엔드는 req_to_token 행을 그대로 page table로 넘긴다. 중간에 복사하는 커널이 없어서, 인코딩된 상위 비트가 디코드되지 않은 채 attention 커널까지 간다.

해결. 1차 대상을 Triton 백엔드로 정한 이유가 하나 더 생겼다. Triton과 FlashInfer는 kv_indices 생성 커널을 거치니까 거기서 디코드하면 된다. FA3까지 지원하려면 page table을 만드는 모든 경로에 디코드 복사를 넣어야 해서 범위 밖으로 뺐다.
