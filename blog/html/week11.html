1. 왜 인덱스인가

KV 슬롯 번호가 뒤집히면 피해가 KV 값 오류보다 크다. 상위 비트가 뒤집히면 KV 풀 밖을 읽어 엔진이 죽는다. 하위 비트가 뒤집히면 다른 요청의 유효한 슬롯을 읽어 요청 사이에 데이터가 섞인다. 그런데 슬롯 번호는 비트를 다 쓰지 않는다. A6000에서 8B 모델이면 KV 풀이 대략 2×10^5 슬롯으로 18비트면 충분하다. int32에는 13비트가 남는다.

2. 비트 배치

bit:  31   30..29   28   27 ........ 23   22 .................... 0
      부호  (미사용)  전체   해밍 체크 5비트    슬롯 번호 23비트 (그대로)
      =0             패리티
  • 슬롯 번호를 하위 비트에 그대로 둔다(systematic). v & data_mask가 곧 슬롯 번호다.
  • 해밍 체크비트 5개와 전체 패리티 1비트로 확장 해밍(SECDED)을 만든다.
  • 부호 비트는 항상 0이다. SGLang이 쓰는 -1 sentinel은 부호 비트가 켜져 있어서 인코딩된 값과 구분된다.
  • int32에는 데이터가 최대 25비트(2^25 슬롯)까지 들어간다. int64는 56비트까지 된다.

데이터를 제자리에 두면 좋은 점이 두 가지 있다. choke point의 디코드가 마스크 한 번과 XOR 몇 번이면 끝난다. 그리고 디코드를 빠뜨린 경로가 있으면 상위 비트 때문에 값이 범위 밖으로 나가서, SGLang store 커널의 device assert에 걸려 바로 멈춘다. 조용히 다른 슬롯을 읽는 일이 없다.

선형 코드라 0의 코드워드는 0이다. SGLang의 zeros 버퍼, padding 슬롯 0, req_to_token의 빈 칸이 모두 그대로 유효한 코드워드라서 따로 초기화할 필요가 없다.

3. 검증

구성 사용 비트 모든 값 왕복 단일 플립 (32비트 전부) 코드 안 이중 플립
int32, 23비트 29 8,388,608개 전부 정상 전부 올바른 슬롯 전부 탐지
int32, 25비트 31 33,554,432개 전부 정상 전부 올바른 슬롯 전부 탐지
int64, 40비트 47 2^20개 표본 정상 전부 올바른 슬롯 전부 탐지

미사용 상위 비트(23비트 구성에서 29, 30번과 부호 비트)의 플립은 정보가 없으므로 디코드할 때 지운다. 삼중 플립은 23비트 구성에서 66%가 조용히 틀린 슬롯이 된다. 일반 확장 해밍 코드와 같은 수준이다.

4. 소비 지점과 choke point

1주차 분석에서 인덱스를 쓰고 읽는 곳을 정리했다.

쓰기 (인코딩 지점)

  • extend: write_req_to_token_pool_triton (prefix와 새 슬롯을 함께 기록)
  • decode: alloc_for_decode_default
  • 트리 삽입 후 행 재지정: checkpoint_into_tree

읽기 (디코드 choke point)

  • create_flashinfer_kv_indices_triton: Triton과 FlashInfer 백엔드가 공유하는 kv_indices 생성 커널. 디코드를 여기 한 곳에 넣으면 attention 경로 전체가 덮인다.
  • 슬롯 할당·해제 경로 (free_pages 조작)
  • // page_size 같은 산술과 torch 인덱싱 직전

out_cache_loc, req_to_token, node.value, free_pages에 같은 코드를 쓰면 구조 사이를 오갈 때 다시 인코딩할 필요가 없다. 인코딩된 값이 31비트 이하라 int64↔︎int32 변환에서도 그대로 유지된다.

주의할 점: FlashAttention 3 백엔드는 req_to_token 행을 그대로 page table로 넘긴다. 별도 복사 커널이 없어서 상위 비트가 커널까지 간다. Triton 백엔드를 1차 대상으로 정한 이유가 하나 더 생긴 셈이다.
