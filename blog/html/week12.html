[RadixMend 12주차] 모듈 B 마무리: 검사 커널 합치기와 free_pages·seq_lens 보호

11주차 끝에 모듈 B는 인덱스 결함을 다 막았지만 TTFT를 두 배로 만들어 놓았다. 12주차에는 그 비용을 없애고, 아직 비어 있던 두 구조(빈 slot 목록 free_pages, 요청별 길이 seq_lens)까지 덮었다.

커널 하나로 합친 효과

11주차에 넣어 둔 두 가지 수정, 인코딩·검사를 Triton 커널 하나로 합친 것과 같은 step 안의 반복 match는 노드당 한 번만 검사하게 한 것을 재 봤다.

구성 TPOT c8 / c32 TTFT c8 / c32
B만, 수정 전 +2.6% / +7.2% +138% / +80%
B만, 수정 후 +0.1% / +0.2% +0.5% / +0.3%

TTFT가 사실상 사라졌다. 커널 launch 수를 줄인 게 거의 전부였다. 비용 문제가 정확성 문제보다 훨씬 빨리 풀린 드문 경우였다.

free_pages는 node.value 방식 그대로

빈 slot 목록이 깨지면 무서운 건, 이미 트리의 다른 노드가 쓰고 있는 slot을 새 요청에 내줄 수 있다는 점이다. 그러면 두 요청이 한 slot에 KV를 덮어쓰게 된다. 다행히 free_pages는 int64라 node.value와 같은 방식(32~38번 비트에 코드, 39번 비트에 표시)을 그대로 쓸 수 있었다. free가 목록에 돌려놓을 때 인코딩하고, alloc이 꺼내 줄 때 검사하고 표시를 뗀다. clear로 목록을 새로 만들 때도 전체를 인코딩한다.

seq_lens는 코드를 붙이지 않고 CPU 사본으로

seq_lens는 GPU 텐서인데, 스케줄러가 CPU 쪽에 같은 값을 seq_lens_cpu로 따로 들고 있다. 이건 매 step 스케줄러가 직접 계산하는 값이라 GPU 쪽보다 믿을 만하다. 그래서 코드를 붙이는 대신, batch를 준비할 때마다 GPU 쪽을 CPU 사본으로 덮어쓰기로 했다. 다르면 몇 개가 달랐는지 센다.

설치하자마자 서버가 안 떴다

처음엔 이 덮어쓰기를 ScheduleBatch.get_model_worker_batch에 걸었다. forward에 넘길 batch를 만드는 곳이라 거기가 맞다고 생각했다. 로컬 테스트는 전부 통과했는데, 서버에 올리니 설치 단계에서 바로 실패했다. SGLang 0.5.22에는 그 함수가 없었다. 로컬 테스트는 가짜 클래스로 감싸기 동작만 봤으니 실제 SGLang에 그 이름이 있는지는 아무도 확인하지 않은 셈이다.

prepare_for_decode와 prepare_for_extend 뒤로 옮겼다. 그리고 다시는 이런 일이 없게 두 가지를 해 뒀다. 하나는 감싸는 대상이 설치된 SGLang에 실제로 있는지 import해서 확인하는 테스트를 모듈마다 넣은 것이다. 다른 하나는 작업 환경에 0.5.22 소스를 풀어 두고, 새로 감쌀 곳은 반드시 그 소스에서 이름과 시그니처를 확인하는 것이다.

복원했는데 여전히 죽었다

옮긴 버전으로 재 보니 free_pages는 하위·상위 비트 모두 30/30 교정, 크래시도 출력 변화도 없었다. node.value와 req_to_token도 회귀가 없었다. 그런데 seq_lens만 실패했다. 하위 비트를 뒤집으면 30회 중 19회 출력이 바뀌었고, 상위 비트를 뒤집으면 30회 전부 크래시였다. 복원하는 코드는 분명 도는데 결과가 이렇다면, 고치는 시점이 너무 늦다는 뜻이었다.

들여다보니 두 군데가 문제였다. 먼저 prepare_for_decode 자체가 seq_lens를 읽는다. 새 slot을 할당하고 req_to_token에 쓰는 데 길이가 필요하다. 그러니 준비가 끝난 뒤에 복원하면 준비 과정은 이미 깨진 길이로 돌아간 다음이다. 그리고 forward가 쓰는 ForwardBatch가 스케줄러의 seq_lens 텐서를 복사하지 않고 그대로 공유하고 있었다. 주입이 그 공유 텐서에 일어나면 스케줄러 쪽에서 복원해도 forward 쪽 값이 뒤늦게 바뀔 수 있었다.

그래서 준비 전과 후에 모두 복원하고, ForwardBatch.init_new에서도 한 번 더 CPU 사본으로 맞춘 뒤, forward에는 스케줄러와 따로 떨어진 텐서를 넘기게 했다. 다시 재니 하위·상위 각 30회, 60회 전부 크래시 0, 출력 변화 0이었다.

모듈 B 최종

대상 무보호 모듈 B
node.value 하위·상위 크래시 11, 출력 변화 29 0, 0
req_to_token 하위·상위 크래시 28, 출력 변화 1 0, 0
free_pages 하위·상위 0, 0 (전부 교정)
seq_lens 하위·상위 0, 0 (CPU 사본으로 복원)

비용은 B만 켰을 때 TPOT c8 +0.4%, c32 +0.3%, TTFT +0.5%, +0.1%, 메모리는 88 MiB다. 이것으로 인덱스 네 가지를 모두 덮었다.

남은 건 둘이다. 2비트 인덱스 오류는 탐지만 하고 아직 따로 조치하지 않는다. 그리고 req_to_token은 attention 길목에서만 검사하니, 그 밖에서 표를 읽는 곳(요청이 끝나 트리에 넣을 때, slot을 반납할 때)은 마지막 forward 이후의 짧은 틈이 남아 있다. 이 중 트리에 넣는 쪽은 한참 뒤 모듈 전체를 다시 점검하면서 막았다.
