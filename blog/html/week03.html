[RadixMend 3주차·선행] Triton 커널을 검증하고, 실험 서버에 맞춰 계획을 고쳤다

3주차 계획에는 "신드롬 계산만 넣은 커널 프로토타입으로 decode·extend 오버헤드 선측정"이 있다. 오버헤드는 GPU가 있어야 잴 수 있지만, 커널이 계산을 맞게 하는지는 CPU에서도 확인할 수 있다. 그래서 그 부분만 먼저 했다. 여기서 만든 커널들은 6~7주차 모듈 A 구현의 뼈대가 된다.

이번 주에는 실험할 GPU도 정했다. 대학교에서 빌릴 수 있는 서버가 CUDA 12.2라서 SGLang 버전을 낮췄고, 처음 계획한 시행 횟수로는 GPU를 너무 오래 잡고 있어야 해서 실험 규모도 줄였다. 이 과정은 트러블슈팅 5~7에 정리했다.

이번 주에 하기로 한 것 (WBS)

  • K·V 텐서 비트 위치별 영향 측정 → GPU 필요, 아직 못 함
  • 커널 검사 프로토타입과 decode·extend 경로별 오버헤드 선측정 → 커널 작성과 정확성 검증은 끝, 오버헤드 측정은 GPU 필요

왜 독립 커널부터 만들었나

최종 목표는 SGLang Triton 백엔드의 decode/extend attention 커널 안, K/V 타일을 읽은 바로 다음에 검사를 넣는 거다. 그런데 처음부터 attention 커널을 고치면 attention 계산 버그와 SECDED 계산 버그가 뒤섞여서 어디가 틀렸는지 찾기 어렵다. 그래서 같은 계산만 하는 커널 세 개를 따로 만들고, 2주차에 검증한 numpy 구현과 비트 단위로 맞췄다.

커널 하는 일 나중에 들어갈 곳
encode_kernel 새로 쓴 K/V 행의 체크워드 계산 KV 저장 커널 (encode-at-store)
check_load_kernel slot 번호로 벡터를 모아 오면서 신드롬 계산, 1비트는 레지스터에서 교정, 오류는 로그에 기록 decode/extend attention의 타일 읽기 직후
scrub_kernel 로그에 남은 벡터를 다시 검사하고 메모리에 고친 값 쓰기 별도 커널 (스텝 사이나 쉬는 시간)

커널에서 하는 계산

원소마다 하는 일은 패리티 계산과 XOR뿐이다.

@triton.jit
def _par16(v):           # 16비트 값의 패리티
    v = v ^ (v >> 8)
    v = v ^ (v >> 4)
    v = v ^ (v >> 2)
    v = v ^ (v >> 1)
    return v & 1

@triton.jit
def _data_terms(x, e_lab, bmask_ptr, B: tl.constexpr):
    par = _par16(x)                                         # 원소별 패리티
    p = tl.sum(par, axis=0) & 1                             # P
    se = tl.reduce(tl.where(par == 1, e_lab, 0), 0, _xor)  # S_e
    sb = p * 0
    for k in tl.static_range(B):                            # S_b: 비트마다 마스크 하나
        m = tl.load(bmask_ptr + k)
        sb = sb | ((tl.sum(_par16(x & m), axis=0) & 1) << k)
    return p, se, sb

교정은 분기 없이 한다. "데이터 오류"로 판정됐고 원소 번호가 맞는 lane만 그 비트를 XOR한다.

fix = tl.where((status == 1) & (d == elem), 1 << bit, 0)
x = x ^ fix    # attention 계산은 고친 값으로 하고, 메모리는 손대지 않는다

커널 안에서 메모리를 바로 고치지 않는 이유는 기술서에 쓴 그대로다. 같은 벡터를 여러 CTA가 동시에 읽을 수 있고(prefix 공유, split-KV, GQA), 3비트 이상 오류를 잘못 고친 값이 메모리에 박히면 안 된다. 1주차에 extend 커널이 같은 prefix 벡터를 여러 번 읽는다는 걸 확인해서 이 분리가 더 중요해졌다.

트러블슈팅

1. GPU가 없는데 Triton 커널을 어떻게 돌리나

문제. Triton 커널은 보통 CUDA GPU에서만 돈다. 개발 환경엔 GPU가 없었다.

해결. TRITON_INTERPRET=1을 켜면 Triton이 커널을 numpy로 해석해서 CPU에서 실행해 준다. 엄청 느리지만 결과는 같아서 정확성 검증엔 충분하다. 테스트 파일은 GPU가 있으면 GPU에서, 없으면 인터프리터 모드일 때만 돌고 그 외엔 건너뛰게 했다. 나중에 GPU 서버에서 같은 테스트를 그대로 돌리면 된다.

2. popcount와 XOR 리덕션을 인터프리터에서 쓰기

문제. 패리티는 보통 popcount로 구하는데, Triton에서 popcount는 CUDA libdevice 함수(popc)를 불러야 하고, 이건 인터프리터에서 쓸 수 없다. 또 S_e는 원소 128개를 XOR로 합쳐야 하는데, tl.sum 같은 내장 XOR 리덕션은 없다.

해결. 패리티는 시프트하고 XOR하는 걸 네 번 반복하는 방식(XOR 접기)으로 바꿨다. GPU에서도 정수 연산 몇 개라 느리지 않다. XOR 리덕션은 tl.reduce에 XOR 결합 함수를 직접 넘겼다. 본 커널을 쓰기 전에 원소 128개를 XOR로 합치는 작은 커널부터 만들어서 numpy 결과와 같은지 먼저 확인했다.

@triton.jit
def _xor(a, b):
    return a ^ b

se = tl.reduce(values, 0, _xor)

3. 같은 벡터가 로그에 여러 번 찍힌다

문제. attention 커널은 같은 벡터를 여러 번 읽을 수 있어서, 오류 하나가 로그에 여러 번 기록된다. scrub 커널이 로그대로 무작정 고치면 같은 비트를 두 번 뒤집어서 원래대로 되돌려 버릴 수 있다.

해결. scrub 커널은 로그를 그대로 믿지 않고, 메모리에서 벡터를 다시 읽어 신드롬을 새로 계산한다. 이미 고쳐진 벡터면 "정상"으로 나와서 아무것도 안 한다. 그 사이에 오류가 더 쌓여서 이제 단일 오류가 아니면 역시 쓰지 않는다. 이렇게 하면 같은 항목을 몇 번 처리해도 결과가 같다. 같은 벡터를 두 번 기록해 놓고 결과가 같은지 테스트로 확인했다.

4. 테스트가 틀렸던 경우

문제. scrub 후에 다시 읽으면 이중 오류 벡터가 로그에 두 번 남을 거라고 테스트를 썼는데 실제로는 한 번이었다.

원인. 커널이 아니라 테스트가 틀렸다. 그 테스트에서 이중 오류 벡터(slot 20)는 읽기 목록에 한 번만 들어 있었다. 두 번 읽은 건 단일 오류 벡터(slot 3) 쪽이었고, 그건 scrub으로 이미 고쳐져서 로그에 안 남는 게 맞다.

해결. 기대값을 1로 고쳤다. 커널 결과를 의심하기 전에 테스트의 전제부터 다시 보는 게 빠르다는 걸 또 배웠다.

5. 빌릴 수 있는 GPU가 CUDA 12.2였다

문제. 실험은 대학교에서 빌릴 수 있는 서버로 하기로 했다. RTX A6000이 7장 꽂혀 있어서 기술서에 적은 GPU와 똑같다. 그런데 CUDA가 12.2였다. 1주차에 고정한 SGLang v0.5.22는 torch 2.14.1, flashinfer 0.7.1이 전부 CUDA 13 빌드라, 드라이버가 580 이상이어야 돌아간다. CUDA 12.2면 드라이버는 535 계열일 가능성이 크다.

원인. SGLang은 v0.5.20부터 CUDA 13 빌드만 배포한다. 공식 설치 문서에도 "CUDA 12 빌드(cu129)가 있는 마지막 버전은 v0.5.19"라고 나와 있다. PyTorch 2.14부터 CUDA 12.9 빌드가 없어진 영향이다.

검토한 방법.

방법 판단
서버 드라이버를 580 이상으로 올리기 가장 깔끔하지만 여러 사람이 같이 쓰는 서버라 내 마음대로 못 한다
CUDA 호환성 패키지(cuda-compat)로 옛 드라이버에서 CUDA 13 쓰기 root 없이 되지만, A6000과 535 드라이버 조합이 지원되는지 확실하지 않다
Colab이나 RunPod 같은 클라우드 GPU 돌아가긴 하지만 돈이 들고, Colab은 세션이 끊길 때마다 다시 설치해야 한다. 둘 다 ECC를 켜고 끌 수 없다
SGLang을 v0.5.19로 낮추기 CUDA 12 빌드가 공식으로 있다. 대신 지금까지 한 코드 분석을 다시 맞춰야 한다

해결. SGLang을 v0.5.19로 낮췄다. v0.5.22보다 한 달 정도 앞선 버전(2026년 9월)이라 큰 구조가 거의 같을 거라고 봤다. 설치는 공식 문서에 나온 CUDA 12 절차를 따른다.

uv pip install --prerelease=allow sglang==0.5.19
uv pip install --force-reinstall torch==2.13.0 torchaudio==2.11.0 torchvision \
    --index-url https://download.pytorch.org/whl/cu129
uv pip install --force-reinstall sglang-kernel --index-url https://docs.sglang.ai/whl/cu129/

CUDA 12.9 빌드가 CUDA 12.2 드라이버에서 도는지는 같은 12 계열 안의 호환성에 기대는 거라 서버에서 직접 확인해야 한다.

6. 버전을 낮추고 나서 한 일

문제. 1주차 코드 분석 문서는 전부 v0.5.22 기준이다. 모듈 A~D를 어디에 끼울지, 결함을 어디에 주입할지가 그 분석에 기대고 있다. 버전을 낮췄는데 설계가 전제하는 사실 하나가 달라지면 그 모듈의 삽입 위치가 통째로 바뀐다.

한 일. v0.5.19와 v0.5.22를 둘 다 받아서, 설계가 기대는 사실을 하나씩 v0.5.19에서 다시 확인했다.

다행히 핵심은 그대로였다.

  • tree는 여전히 UnifiedRadixCache이고, 노드의 value는 req_to_token 행을 int64로 복사한 GPU 텐서다. 모듈 B의 교차 복구 원천으로 쓸 수 있다.
  • KV free list(free_pages)는 GPU int64 텐서이고, req_to_token은 int32다.
  • KV 저장 커널은 JIT CUDA store_cache이고, Triton backend도 그대로 있다.
  • 다음 decode 입력 토큰을 GPU FutureMap.output_tokens_buf에서 가져오는 구조, seq_lens_cpu 미러, 체크워드 크기를 더할 _compute_cell_size도 다 있다.
  • 실험에 쓰는 서버 옵션(--kv-canary, --cuda-graph-backend-decode, --disable-overlap-schedule)도 있다.

달라진 건 다섯 가지였고, 하나씩 조치했다.

달라진 것 v0.5.22 v0.5.19 조치
tree core 기본값 Rust (노드 접근 불가) Python 오히려 편해졌다. 그래도 실행 스크립트에 SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND=python을 적어 두고, "Rust 대비 처리량 비교" 항목은 뺐다
tree 삽입 API checkpoint_into_tree cache_finished_req, cache_unfinished_req 해시 비교 기법의 digest 계산과 모듈 C의 삽입 게이팅 위치를 이 두 함수로 옮겼다
Triton의 KV 인덱스 생성 KVIndexTranslator를 거침 _fill_kv_indptr_and_indices에서 바로 생성 모듈 B의 decode를 이 함수 한 곳에 넣으면 일반 경로와 CUDA graph 경로를 같이 덮는다. 한 단계 단순해졌다
GPU 해시 커널 adler32.py(Adler-32) 있음 없음, gpu_tensor_hash.py만 있음 비교 기법의 빠른 해시 버전을 gpu_tensor_hash로 바꿨다
component 파일 이름 full.py, base.py full_component.py, tree_component.py 경로만 바꿨다

결과는 docs/sglang_v0519_diff.md에 따로 정리했다. 기존 분석 문서의 줄 번호는 v0.5.22 기준으로 남겨 두고, 패치할 때는 이 차이 문서를 먼저 보기로 했다. 실험 명세의 환경 표도 v0.5.19(torch 2.13.0, cu129)로 고쳤다.

여기서 배운 건, 버전을 고정해 둔다고 끝이 아니라는 점이다. 분석 문서에 "어떤 사실에 기대고 있는지"를 따로 정리해 둔 덕에 다시 확인할 목록이 바로 나왔다.

7. 계획한 시행 횟수로는 GPU를 너무 오래 잡는다

문제. 실험 명세에는 비트 위치 16개마다 150회씩 돌리는 식으로 시행 횟수를 잡아 뒀다. K와 V, 위치, 인덱스, 교정 검증, 봉쇄·복구를 다 더하니 서버 시행이 약 13,000회였다. 시행 하나가 30초~1분이라고 치면 개발과 비용 측정까지 합쳐 **GPU 200~400시간**이 나온다. 공용 서버에서 GPU 한 장을 이렇게 오래 붙잡고 있을 수는 없다.

해결. 통계적으로 의미가 남는 선에서 시행 수를 줄였다. 원칙은 두 가지다.

  1. 넓게 훑을 때는 적게, 중요한 곳에만 많이. 비트 16개는 50회씩만 돌린다. 50회면 신뢰구간이 ±14%p 정도라 비트 사이의 큰 차이는 충분히 보인다. 영향이 큰 비트 4개만 150회로 늘려서 선행 연구와 같은 조건으로 비교한다.
  2. 결과가 거의 정해진 항목은 적게. 크래시나 1비트 교정 성공처럼 될지 안 될지가 거의 정해진 항목은 30회 이하로 줄였다. 교정률은 서버를 돌리는 대신 커널 단위로 전수 검사하는 테스트를 주된 근거로 쓴다.

시행 하나도 가볍게 만들었다. 요청은 200개 대신 20개만 쓰고(공유 prefix는 그대로 둔다), 출력은 64토큰에서 자르고, golden 출력은 조건마다 한 번만 만들어 재사용한다.

처음 계획 줄인 계획
서버 시행 수 약 13,000회 약 2,500회
예상 GPU 시간 200~400시간 80~150시간

시행당 시간은 아직 재 보지 않아서 위 숫자는 추정이다. 첫날 시행 하나에 걸리는 시간을 재고 다시 맞출 생각이다. 효과가 50% 근처로 애매하게 나오는 조건이 있으면 그 조건만 150회로 늘린다.

아직 모르는 것

  • 오버헤드. 인터프리터는 느려서 속도를 재 봐야 의미가 없다. GPU에서 decode와 extend를 따로 재야 한다. 목표는 TPOT 증가 3% 미만이다.
  • attention 커널 안으로 옮기기. decode 커널은 K 타일이 [BLOCK_DMODEL, BLOCK_N] 모양이라 열 하나가 벡터 하나다. 리덕션 방향이 독립 커널과 달라서 옮길 때 다시 맞춰야 한다.
  • v0.5.19 cu129 빌드가 서버에서 도는지. CUDA 12.2 드라이버에서 torch와 Triton 커널이 정상 동작하는지 첫날 확인해야 한다.
