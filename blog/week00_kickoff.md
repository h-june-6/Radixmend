# [RadixMend 킥오프] KV 캐시의 비트 하나가 수백 개 요청을 바꾼다면

> 앞으로 16주 동안 진행할 RadixMend 프로젝트를 소개하는 글이다. SGLang의 radix tree KV 캐시에서 비트가 뒤집혔을 때, attention 커널이 KV를 읽는 그 순간에 바로 고치는 소프트웨어 대응책을 만든다.

## 한 줄로 말하면

토큰·KV 헤드 벡터(256바이트)마다 15비트짜리 오류 정정 코드를 붙인다. 1비트 오류는 재계산 없이 읽는 순간 고치고, 메모리에 있는 값까지 되돌려 놓는다. 2비트 오류는 잡아내서 다시 계산한다. 메모리는 KV의 0.8% 정도만 더 쓴다.

## 왜 이 문제를 골랐나

### 공유하면 같이 망가진다

SGLang은 KV 캐시를 radix tree로 관리한다(RadixAttention). 시스템 프롬프트나 few-shot 예시처럼 여러 요청이 같은 앞부분(prefix)으로 시작하면, 그 부분의 KV는 메모리에 **딱 한 벌만** 둔다. 메모리도 계산도 크게 아낄 수 있다.

반대로 보면, 그 한 벌에서 비트 하나만 뒤집혀도 그 prefix를 쓰는 요청 전부와 그 아래 자식 노드로 피해가 번진다. 루트 가까운 노드는 거의 모든 요청이 읽는다. 게다가 SGLang 스케줄러(LPM)는 캐시된 노드를 쓰는 요청을 먼저 처리해서, 공유 노드는 더 자주 읽힌다.

### 비트플립은 실제로 일어나고, 티가 잘 안 난다

- vLLM의 prefix caching을 대상으로 한 선행 연구(Yamamoto & Matsuura, 2026)는 공유 KV 블록의 value 텐서에서 비트 하나를 뒤집어 봤다. BF16의 16개 비트 위치 중 13곳에서, 출력이 **문장으로는 멀쩡한데 내용이 원래와 달라졌다.** 정답을 모르면 망가진 줄도 모른다는 얘기다. 가수부 맨 아래 비트 하나만 뒤집어도 시행의 64%에서 적어도 요청 하나의 출력이 바뀌었다(Qwen3-8B).
- 피해는 시간이 지나도 줄지 않았다. 망가진 블록이 캐시에 남아 있는 동안 뒤에 오는 요청이 계속 영향을 받아서, 피해 요청 수가 요청 수에 비례해 늘었다.
- 하드웨어 공격도 실제로 나왔다. GDDR6를 쓰는 RTX A6000에서 Rowhammer로 비트를 뒤집는 데 성공했고(GPUHammer), KV 캐시의 특정 위치를 노리는 공격(CacheTrap), GPU 페이지 테이블을 건드려 권한을 올리는 공격(GDDRHammer, GeForge)도 보고됐다. 한 영역에서 여러 비트가 같이 뒤집힐 수 있다는 것도 보여 줬다.
- 그런데 GDDR을 쓰는 GPU는 하드웨어 ECC가 보통 **꺼져 있다.**

### radix tree라서 생기는 문제 두 가지

선행 연구는 value 텐서만 봤다. radix tree 구조에서는 문제가 두 개 더 있다.

**파생 오염.** 부모 노드 P의 ℓ번째 레이어가 망가진 상태에서 그 아래 자식 C가 prefill되면, C의 ℓ+1번째 레이어부터는 망가진 P를 보고 계산된다. 나중에 P를 고쳐도 C는 틀린 채로 남는다. C의 체크섬은 C 자신의 (틀린) 값으로 계산돼서 앞뒤가 맞기 때문에, 데이터 체크섬으로는 못 잡는다.

**인덱스 오염.** 트리 노드 자체는 호스트 메모리의 Python 객체지만, 각 노드가 가리키는 KV 슬롯 번호 목록과 요청별 슬롯 번호 표는 GPU 메모리에 있다. 슬롯 번호의 위쪽 비트가 뒤집히면 KV 풀 밖을 읽어서 엔진이 죽고, 아래쪽 비트가 뒤집히면 다른 요청의 KV를 읽어서 요청끼리 데이터가 섞인다.

## 기존 방법으로는 왜 안 되나

| 기법 | 대상 | 한계 |
|---|---|---|
| hit 시점 해시 (선행 연구) | vLLM 공유 prefix 블록 | 검사하고 실제로 쓰기까지의 틈(TOCTOU)에서 생기는 파생 오염은 못 막음. 잡기만 하고 고치지는 못함 |
| GPU 하드웨어 ECC | DRAM 전체 | A6000 기준 메모리 6.25% 손해, 대역폭 최대 12% 저하. GDDR에서는 기본으로 꺼져 있음 |
| ABFT 계열 | attention 연산 | 계산 중에 나는 오류가 대상. 캐시에 보관 중인 값이 깨지는 건 못 봄 |
| SAVE, DNN용 소프트웨어 ECC | 모델 가중치 | 실행 중에 생기고 공유되는 KV는 대상이 아님 |
| SGLang PD 전송 체크섬 | PD 분리 환경의 KV 전송 | 전송 직후 한 번만 검사, 잡기만 함, 기본값 꺼짐 |

정리하면, 기존 방법은 KV가 깨진 걸 **잡기만** 하거나, 연산 오류나 가중치를 대상으로 하거나, radix tree의 prefix 공유와 안 맞는다.

## 핵심 아이디어: KV가 쓰이는 방식을 이용한다

KV 캐시는 일반 메모리와 쓰이는 방식이 다르다. 이걸 잘 이용하면 하드웨어 ECC보다 훨씬 싸게, 잡는 걸 넘어 고치는 것까지 할 수 있다.

1. **한 번 쓰고 나면 읽기만 한다.** 토큰의 KV는 계산될 때 한 번 저장되고, 슬롯이 풀릴 때까지 안 바뀐다. 쓸 때 코드를 한 번 만들어 두면 끝이고, 읽고-고치고-다시 쓰는 비용이 없다.
2. **항상 벡터 통째로 읽는다.** attention 커널은 토큰·KV 헤드마다 head_dim 전체를 한 번에 읽는다. 그래서 코드 블록을 2048비트로 크게 잡을 수 있고, 체크 비트 15개면 SECDED가 된다. 하드웨어 ECC(6.25%)의 8분의 1 정도다.
3. **KV를 읽는 곳은 attention 커널뿐이다.** decode와 extend 커널 두 곳만 검사하면 KV를 쓰는 모든 경로가 검사를 거친다.

hit 시점에 한 번 검사하는 게 아니라 **읽을 때마다** 검사한다. 중간 구간마다 지키는 대신 끝에서 끝까지(end-to-end) 지키는 셈이다.

## 시스템 설계: 모듈 네 개

### 모듈 A: 읽는 순간 스스로 고치기

- 벡터마다 15비트 체크워드(P, 원소 라벨 XOR, 비트 라벨 XOR, 전체 패리티)를 붙인다. KV를 저장하는 커널에서 체크워드도 같이 만들어서, 저장과 인코딩 사이에 무방비한 순간을 없앤다.
- decode/extend attention 커널이 K/V 타일을 읽자마자 신드롬을 계산한다. 1비트 오류면 레지스터에서 바로 고쳐서 attention 계산에 쓴다.
- 메모리는 커널 안에서 고치지 않고, 오류 위치를 로그에 남긴다. 별도 scrub 커널이 다시 검사한 다음 메모리에 쓴다. 같은 벡터를 여러 블록이 동시에 읽을 때 중복으로 쓰는 걸 피하고, 3비트 이상 오류를 잘못 고친 값이 메모리에 박히는 걸 막기 위해서다.
- 잘 안 읽히는 노드는 한가할 때 돌면서 검사한다(백그라운드 scrubbing). 1비트 오류가 쌓여서 2비트가 되기 전에 고치려는 거다.
- 데이터 비트에 붙이는 라벨은 키로 섞은 비밀 순열이다. 비트를 3개 이상 뒤집을 수 있는 공격자도 원하는 대로 잘못 고치게 만들기 어렵다.

### 모듈 B: 스스로 고치는 인덱스

GPU에 있는 인덱스 텐서(`req_to_token`, `node.value`, 빈 슬롯 목록, `seq_lens`)의 **안 쓰는 위쪽 비트**에 SECDED 코드를 넣는다. 메모리는 하나도 안 늘어난다. 디코드는 몇 군데(`kv_indices` 생성 커널, 슬롯 할당·해제)에 모아서 한다. 2비트 오류가 나면, 트리 경로의 `node.value`와 요청의 `req_to_token`이 같은 정보를 갖고 있다는 걸 이용해서 서로에게서 복구한다.

### 모듈 C: 읽기 검사와 계보 기반 복구

- 모든 읽기가 검사를 거치니까, 망가진 부모를 읽어서 자식이 망가지는 파생 오염이 처음부터 막힌다.
- 2비트 이상이 잡히면 요청별 오류 플래그를 다음 토큰 복사에 실어서 스케줄러로 보낸다. 그 스텝의 KV와 샘플링한 토큰은 버린다.
- 망가진 노드에 poisoned 표시를 하고, prefix 매칭이 그 앞에서 멈추게 한다. 그 노드를 쓰던 요청은 다시 대기열에 넣고, 참조가 0이 되면 노드를 해제한다.
- 노드마다 `born_epoch`, `clean_epoch`를 기록해 둔다. 검사에 빈틈이 있었던 경우, 오염 이후에 생긴 자손만 골라서 무효화할 수 있다.

### 모듈 D: 많이 공유되는 곳은 더 두껍게

제일 많이 공유되는 첫 레벨 노드(루트의 자식)와 attention sink 토큰의 K/V는 사본을 하나 더 둔다. 2비트 오류가 나도 재계산이나 재등록 없이 사본에서 바로 되살린다. 목적은 계산을 아끼는 게 아니라 **피해 범위를 줄이는 것**이다. 많이 공유된 노드가 poisoned되면 그걸 쓰는 요청을 전부 다시 돌려야 하기 때문이다.

## 위협 모델과 보호 범위

- 오류 원인: 무작위 soft error, 전송 오류, Rowhammer 같은 의도적인 비트플립
- 공격자: 같은 GPU를 쓰는 다른 사용자. KV에 직접 쓸 권한은 없고, 비트를 뒤집게 만들 수만 있다.
- 보장: 벡터 하나(256바이트) 안에서 뒤집힌 비트가 2개 이하일 때. 3개 이상은 비밀 라벨로 확률적으로만 막는다.
- 범위 밖: KV를 계산하는 연산 자체가 틀리는 경우. 트리 노드 객체는 ECC가 켜진 호스트 메모리에 있다고 본다.

| 공격 대상 | 아무것도 안 하면 | RadixMend |
|---|---|---|
| K/V 벡터 1비트 | 출력이 몰래 바뀜 | 읽는 순간 고치고 메모리도 복원 |
| K/V 벡터 2비트 | 출력이 몰래 바뀜 | 잡아내고 다시 계산 |
| 슬롯 인덱스 1비트 | 엔진이 죽거나 요청끼리 KV가 섞임 | 고침 |
| 빈 슬롯 목록 | 한 슬롯을 두 요청이 받아서 KV가 섞임 | 1비트 고침, 2비트 잡아냄 |
| 파생 오염 | 계속 틀린 채로 남음 | 잡을 수 있는 오류라면 처음부터 막음 |

## 어떻게 평가하나

소프트웨어로 결함을 주입하는 실험으로 네 가지 질문에 답한다. 주된 비교 대상은 선행 연구의 hit 시점 해시 기법을 SGLang에 옮긴 버전이다.

- **RQ1 특성 분석**: radix tree에서 피해가 어떻게 퍼지나. K와 V는 뭐가 다른지, attention sink 위치는 어떤지, 인덱스가 깨지면 어떻게 되는지
- **RQ2 정확성·교정**: 평소 동작이 그대로인지, 비트 위치별 1비트 교정률(목표 100%), 체크비트가 깨져도 데이터가 무사한지, 2비트 탐지율
- **RQ3 비용**: TPOT, TTFT, 처리량, 메모리. decode와 extend를 따로 잰다(목표: TPOT 증가 3% 미만)
- **RQ4 봉쇄·복구**: 영향받은 요청 수, 파생 오염된 노드 수, 다시 계산하는 데 걸리는 시간
