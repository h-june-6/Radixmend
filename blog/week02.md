# [RadixMend 2주차] 2063비트 코드워드의 모든 오류를 세어 보다: SECDED 참조 구현과 전수 검증

> RadixMend 16주 계획 중 2주차 기록이다. 이번 주의 핵심은 KV 헤드 벡터 하나(256바이트)를 15비트로 지키는 SECDED 코드가 설계대로 동작하는지 하나도 빼지 않고 확인하는 것이었다.

## 이번 주 목표 (WBS)

- 결함 주입 도구 완성 (KV 텐서, 슬롯 인덱스)
- 무결함 기준선 측정 (출력, TPOT, TTFT, 처리량, 메모리)
- SECDED 참조 구현 및 단위 테스트: 체크비트 포함 전체 코드워드 기준 단일 오류 전수 교정, 이중 오류 전수 탐지

이 중 기준선 측정은 GPU가 필요해서 아직 하지 못했다. 나머지 두 개는 CPU에서 끝냈다.

## 1. 코드 구조 복습

bf16 헤드 벡터 하나는 128원소 × 16비트 = 2048 데이터 비트다. 각 데이터 비트에 (원소 번호 e, 비트 위치 b) 라벨을 붙이고, 체크워드를 이렇게 만든다.

| 필드 | 비트 수 | 의미 |
|---|---|---|
| P | 1 | 데이터 전체 패리티 |
| S_e | 8 | 패리티가 홀수인 원소들의 e-라벨 XOR |
| S_b | 5 | 1인 데이터 비트 전부의 b-라벨 XOR |
| Q | 1 | 데이터 + P + S_e + S_b 전체 패리티 |

합쳐서 15비트이고 int16 하나에 들어간다. KV 대비 메모리는 2/256 = 0.78%다.

라벨은 0을 뺀 값 중에서 키로 섞은 비밀 순열로 고른다. 0을 빼는 이유는 라벨 0인 데이터 비트의 오류가 P 비트 오류와 같은 신드롬을 내기 때문이다. 순열은 BLAKE2b keyed 모드로 만들어서, 같은 키면 어느 기계에서나 같은 라벨이 나온다.

```python
from radixmend.secded_vec import VecCode

code = VecCode()                 # 128원소, E=8, B=5, 15비트
cw = code.encode(x)              # x: uint16[..., 128]  (bf16을 비트 패턴으로 본 것)
x_fixed, cw_fixed, status, pos = code.decode(x_received, cw_received)
```

## 2. 판정 규칙

디코드할 때 신드롬 (ΔP, ΔS_e, ΔS_b, ΔQ)를 구한다. ΔQ는 받은 코드워드 전체의 패리티다.

| 조건 | 판정 |
|---|---|
| 신드롬 전부 0 | 정상 |
| ΔQ=1, ΔP=1, ΔS≠0, 두 라벨이 모두 유효 | 데이터 비트 (e, b) 오류, 교정 |
| ΔQ=1, ΔP=1, ΔS=0 | P 비트 오류 |
| ΔQ=1, ΔP=0, ΔS가 단위 벡터 | S 비트 하나의 오류 |
| ΔQ=1, ΔP=0, ΔS=0 | Q 비트 오류 |
| ΔQ=0, 신드롬≠0 | 2비트 오류, 탐지 |
| 그 밖 | 3비트 이상, 탐지 |

체크비트 오류는 데이터를 건드리지 않고 체크워드만 다시 쓴다. 이 규칙을 15비트 신드롬 2^15개 전부에 적용해 결정표를 만들었다. 커널에서는 같은 규칙을 분기 몇 개로 계산한다.

## 3. 어떻게 "전수" 검증하나

이 코드는 GF(2) 위에서 선형이다. 그래서 오류 패턴의 신드롬은 뒤집힌 위치들의 패리티 검사 행렬 열을 XOR한 값과 같다. 데이터 값과 상관이 없다. 위치마다 열을 하나씩 구해 두면, 어떤 오류 조합이든 XOR 몇 번으로 판정을 확인할 수 있다.

```python
cols = code.columns()                      # 2063개 위치의 신드롬
j, k = np.triu_indices(len(cols), 1)       # 모든 2비트 조합
assert (code.lut_status[cols[j] ^ cols[k]] == DETECTED).all()
```

이렇게 하면 데이터 2048비트와 체크비트 15비트를 합친 2063비트 전체에 대해 다음을 셀 수 있다.

- 단일 오류 2,063개
- 이중 오류 2,126,953개
- 삼중 오류 1,461,216,711개 (약 15억 개, CPU로 12초)

## 4. 결과

| 검사 | 결과 |
|---|---|
| 단일 오류 | 2,063 / 2,063 정확한 위치에서 교정 |
| 이중 오류 | 2,126,953 / 2,126,953 탐지 (오교정 0, 정상 판정 0) |
| 실제 bf16 데이터로 단일 오류 전부 | 6,189건 모두 원래 값과 체크워드로 복원 |
| 실제 데이터로 무작위 이중 오류 | 2,000 / 2,000 탐지 |
| popcount 인코딩 vs 정의대로 인코딩 | 일치 |

마지막 항목은 커널이 쓸 방식을 검증한 것이다. S_b의 k번째 비트는 "b-라벨의 k번째 비트가 1인 위치만 고르는 마스크 M_k"를 써서 `parity(Σ popcount(x_i & M_k))`로 구할 수 있다. 원소마다 popcount 다섯 번이면 되므로 GPU에서 싸다. 이 방식의 결과가 비트를 하나씩 도는 정의와 같은지 확인했다.

코드워드를 2개, 4개로 나눈 경우(64원소, 32원소)도 똑같이 전수 검증했고, 모두 단일 교정·이중 탐지를 만족했다.

## 5. 예상하지 못한 숫자: 삼중 오류

삼중 오류는 SECDED의 보장 밖이지만 15억 개를 다 셀 수 있으니 세어 봤다.

| 라벨 | 삼중 오류 중 조용히 오교정되는 비율 |
|---|---|
| 순차 라벨 (1..128, 1..16) | 75.5% |
| 비밀 순열 라벨 | 27.1% (키 4개 평균) |

비밀 라벨은 공격자가 원하는 오교정을 고르지 못하게 하려고 넣은 것이었다. 그런데 오교정률 자체가 75% → 27%로 크게 떨어졌다. 이유는 라벨 공간이 비기 때문이다. 순차 라벨은 1~128, 1~16을 꽉 채워 쓰지만, 순열 라벨은 8비트 공간 255개 중 128개, 5비트 공간 31개 중 16개만 쓴다. 3비트 오류의 신드롬이 쓰지 않는 라벨에 떨어지면 "탐지"가 된다. 대략 (128/255) × (16/31) ≈ 26%로, 측정값과 맞는다.

이 관찰에서 개선안이 하나 나왔다. 이건 5주차 글에서 다룬다.

## 6. 결함 주입 도구 완성 (CPU까지)

1주차에 시작한 주입기에 인덱스 텐서 주입과 기록 기능을 더했다.

- `inject_index`: `req_to_token`(int32), `node.value`·`free_pages`·`seq_lens`(int64)의 원하는 비트를 뒤집는다. int32 부호 비트(31번)도 정확히 처리한다.
- `sample_kv_faults`: 한 벡터 안에 서로 다른 k비트를 고르는 무작위 샘플러. 다중 비트 실험용이다.
- 모든 플립은 원래 비트, 바뀐 비트, bf16 값 변화와 함께 JSONL로 기록된다. `revert`로 되돌릴 수 있어서 서버 하나로 시행을 반복할 수 있다.

SGLang 서버 프로세스 안에 붙이는 부분은 GPU에서 서버를 띄워야 확인할 수 있어서 다음으로 미뤘다.
